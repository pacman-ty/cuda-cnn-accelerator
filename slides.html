The Project

What it is and why it matters

Project Overview

A CNN inference engine written in Rust with a hand-written CUDA kernel for GPU acceleration.

What it does

  • Takes a pre-trained CNN and runs inference (forward pass) on hundreds of 100×100 input matrices
  • Produces a 10-element output vector for each input
  • Two execution modes: CPU reference and GPU-accelerated CUDA
  • GPU version must produce identical results to CPU (verified with floating-point tolerance)

Why it matters

  • CNN inference is the backbone of deployed ML — image classification, object detection, etc.
  • In production, inference speed is everything — CPU to GPU can mean real-time vs. unusable
  • Forced me to understand what happens underneath PyTorch/TensorFlow when calling model.forward()

Technology Choices

Why Rust?

  • Memory safety without garbage collection — critical for manual GPU memory management
  • Ownership model prevents data races at compile time between host and device
  • Zero-cost abstractions — iterators and closures compile to the same code as hand-written C
  • rustacuda crate — safe Rust bindings over CUDA's C driver API

Why CUDA?

  • NVIDIA target with the most mature tooling
  • Direct control over thread hierarchy, shared memory, and synchronization
  • CNN pipeline maps naturally to CUDA's execution model

Why not PyTorch / TensorFlow?

  • Goal was to understand what those frameworks do internally
  • Writing kernels by hand forces you to think about memory access patterns, thread mapping, and reduction
  • The difference between using a tool and understanding a tool
Key insight: Rust's type system extends safety to the GPU boundary. The DeviceCopy trait prevents accidentally copying types with pointers to device memory.

Design Patterns

  • Strategy Pattern via Closures — for_each_input() takes a closure that decides CPU vs GPU at runtime. I/O logic is decoupled from computation
  • Newtype + #[repr(transparent)] — structs have identical memory layout to inner arrays, enabling zero-cost memcpy to GPU
  • RAII for GPU Resources — CudaContext owns all device memory; Rust's drop ordering frees everything automatically
  • Build-time Codegen — nvcc compiles CUDA to PTX at build time, embedded into the binary via include_str!()

RAII & Drop Ordering

pub struct CudaContext {
    // GPU memory -- dropped FIRST
    input_matrix:  DeviceBox<InputMatrix>,
    conv_output:   DeviceBox<ConvOutput>,
    output:        DeviceBox<OutputVec>,
    conv_layer:    DeviceBox<ConvLayer>,
    output_layer:  DeviceBox<OutputLayer>,

    module: Module,
    stream: Stream,

    // CUDA context -- dropped LAST
    _context: Context,
}

Why order matters

  • Rust drops struct fields in declaration order
  • GPU memory (DeviceBox) must be freed before the CUDA context that owns it
  • If _context drops first → segfault (freeing device memory after context is gone)
  • This is a Rust-specific subtlety — in C++ CUDA you manually call cudaFree then cudaDeviceReset
The underscore prefix in _context tells Rust "I'm keeping this alive for its side effects (drop behavior), not because I use it directly."

The CUDA Kernels

The core of the implementation

Kernel 1: Fused Convolution + ReLU

__global__ void conv_relu(
    double input[100][100],
    double filters[10][5][5],
    double output[10][20][20]
) {
    int tid = blockIdx.x * blockDim.x
            + threadIdx.x;
    if (tid >= 4000) return;

    // Decompose 1D thread ID -> 3D index
    int f     = tid / (20 * 20);
    int rem   = tid % (20 * 20);
    int out_r = rem / 20;
    int out_c = rem % 20;

    int in_r = out_r * 5;
    int in_c = out_c * 5;

    // 5x5 dot product
    double sum = 0.0;
    for (int x = 0; x < 5; x++)
      for (int y = 0; y < 5; y++)
        sum += input[in_r+x][in_c+y]
             * filters[f][x][y];

    // Fused ReLU
    output[f][out_r][out_c] =
        (sum > 0.0) ? sum : 0.0;
}

Design Decisions

  • 4,000 threads — one per output element (10 filters × 20 × 20), all completely independent
  • 1D → 3D mapping — flat thread ID decomposed via division/modulo into (filter, row, col)
  • Fused ReLU — CPU has convolution and ReLU as separate passes; fusing avoids writing 4,000 doubles to global memory and reading them back
  • Each thread does one 5×5 dot product (25 multiply-adds) — small enough to keep in registers
Kernel fusion is a key GPU optimization. Eliminating the intermediate write/read saves ~64KB of global memory traffic per inference.

Kernel 2: Output Layer — Shared-Memory Reduction

__global__ void output_layer(
    double* conv_output,
    double weights[10][4000],
    double* result
) {
    __shared__ double partial[256];
    int neuron = blockIdx.x;
    int tid    = threadIdx.x;

    // Phase 1: strided accumulation
    double sum = 0.0;
    for (int i = tid; i < 4000; i += 256)
        sum += conv_output[i]
             * weights[neuron][i];
    partial[tid] = sum;
    __syncthreads();

    // Phase 2: tree reduction
    for (int s = 128; s > 0; s >>= 1) {
        if (tid < s)
            partial[tid] += partial[tid + s];
        __syncthreads();
    }

    if (tid == 0)
        result[neuron] = partial[0];
}

Two-Phase Strategy

  • 10 blocks (one per output neuron), 256 threads each
  • Phase 1: Each thread accumulates ~16 elements with stride loop — coalesced access, even work distribution
  • Phase 2: Classic tree reduction in shared memory — halves active threads each step: 128 → 64 → ... → 1

Why shared memory?

  • __shared__ is on-chip SRAM — ~100x faster than global memory
  • Partial sums stay on-chip during the entire reduction
  • O(log n) parallel steps vs O(n) sequential — 8 steps instead of 256
Critical: __syncthreads() must be outside conditionals. If placed inside if (tid < s), threads that skip it never hit the barrier → deadlock.

Rust-CUDA Bridge

Initialization (once)

  1. Initialize CUDA runtime & select GPU 0
  2. Create CUDA context (owns all GPU state)
  3. Load compiled PTX kernel module
  4. Create non-blocking stream
  5. Pre-allocate all GPU memory buffers
  6. Copy CNN weights to GPU (persist across all calls)
CNN weights are copied once. Only the input matrix transfers per inference call.

Per-Inference Call

  1. Copy input matrix CPU → GPU
  2. Launch conv_relu kernel (4,000 threads)
  3. Launch output_layer kernel (10 × 256 threads)
  4. Synchronize stream (wait for GPU)
  5. Copy 10-element result GPU → CPU
Both kernels launch on the same stream — CUDA guarantees serial execution. Only one synchronize() needed at the end.

Why floating-point tolerance?

  • FP addition is not associative: (a+b)+c ≠ a+(b+c)
  • GPU sums in different order (parallel tree reduction vs sequential)
  • Small rounding differences accumulate over 4,000-element dot products
  • math.isclose() handles this with relative + absolute tolerance

Memory Safety via Rust

  • No manual malloc/free — DeviceBox handles allocation via RAII
  • Borrow checker prevents host/device data races at compile time
  • Only unsafe: launch! macro calls and DeviceCopy trait impls (both justified by type layout guarantees)

Most Challenging Parts

  • Drop ordering for GPU resources — If CUDA Context drops before DeviceBox allocations, the driver panics. Fix: declare DeviceBox fields first in the struct. A subtle Rust-specific footgun that doesn't exist in C/C++ CUDA
  • Thread-to-data mapping — Decomposing a flat 1D thread ID into the correct 3D (filter, row, col) index, then mapping back to the right 5×5 input region. Wrong division/modulo = garbage output with no error — it's all legal memory access, just wrong indices
  • Shared-memory reduction correctness — __syncthreads() must be reached by every thread in the block. Placing it inside a conditional branch causes deadlock because inactive threads never hit the barrier
  • Debugging GPU code — No practical printf debugging on device. Process: verify thread math on paper, test with small inputs, check memory layouts between Rust and CUDA, add temporary copy-backs to inspect intermediate results

What I'd Improve With More Time

  • Batch processing — Currently one matrix per kernel launch (~5–10μs overhead each). With 250 inputs, that's 500 launches. Batching into 2 launches would amortize this cost dramatically
  • Shared memory for convolution — Load input tiles into shared memory to reduce redundant global memory reads when multiple filters access overlapping regions
  • Warp-level reduction — Last 5 reduction steps (32 elements = 1 warp) execute in lockstep. Using __shfl_down_sync instead of __syncthreads() would eliminate barrier stalls
  • Stream overlap — Use multiple CUDA streams to overlap data transfer of input N+1 with computation of input N, hiding transfer latency
  • f32 / f16 precision modes — Consumer GPUs have up to 32x more f32 throughput than f64. Adding a single-precision mode would be a massive speedup for applications where reduced precision is acceptable

Key Takeaways

  • GPU programming is about data movement, not just parallelism — Minimizing host-device transfers (copy weights once) and fusing kernels (conv + ReLU) mattered more than the parallel algorithms themselves
  • Rust's ownership model extends to GPU resources — RAII for device memory, compile-time enforcement of ownership, DeviceCopy trait preventing unsafe memcpy of pointer types
  • Understanding what frameworks abstract away is valuable — After writing convolution by hand, I have deeper intuition for why certain layer configurations are fast/slow, why batch size matters, and what GPU utilization means
  • A reference implementation makes GPU debugging tractable — Every bug could be isolated by comparing CPU vs GPU output. Without this, debugging would be guessing in the dark
